# Orbit Disk: scan and search design

## Hover responsiveness (0.9.1)

Hover no longer dims unrelated branches. Crossing a sector gap therefore leaves every branch color unchanged. The colored Canvas and collection marks sit in an equatable base layer keyed by presentation revision and metrics; a separate Canvas draws at most the hovered and selected outlines. Collection, folder-publication and geometry changes invalidate the appropriate layer.

Native hit testing caches the exact sector paths until the root, layout revision or metrics change. Each mouse-move event resolves its segment once for both the cursor and highlight. Optimized microbenchmarks over 1,024 pointer positions measured 30.836 → 1.865 ms with 72 sectors and 317.754 → 25.652 ms at the 768-sector cap (16.5× and 12.4× faster). Exact path containment, including boundaries and gaps, is preserved.

Leaving the map skips list scanning; a single related row scrolls directly to its identifier. Group relationship results survive leaving and re-entering a segment. The cache retains immutable member arrays and compares their storage identity in bounded buffer scopes, invalidating on changed members, map revisions, navigation and filtering. Re-entering a synthetic 100,000-member group measured 146.67 → 0.0018 ms median; first-entry relationship work remains unchanged. These measurements cover specific calculations, not whole-app frame rate or input-to-display latency.


## Public updates (0.9.0)

Sparkle 2.10.1 is pinned in SwiftPM and bundled with the app. The public GitHub latest-release asset serves the appcast; downloads require no GitHub account or user token. Only update metadata and app downloads use the network. Scan contents and indexed paths are not included in update requests. Sparkle checks daily while the app is running, and the user chooses installation and restart. [Sparkle setup](https://sparkle-project.org/documentation/) and [publishing](https://sparkle-project.org/documentation/publishing/).

Both the appcast and universal ZIP carry Ed25519 signatures. The public verification key is embedded in the app; the private key belongs only in the maintainer's Keychain and release secret. Signed-feed validation is required with no expiration fallback, and the archive is verified before extraction. Tag releases build both arm64 and x86_64 for macOS 14, verify signatures and metadata, upload all assets to a draft, then publish it. Release validation rejects mismatched versions, non-increasing build numbers, incomplete Apple credentials, and an unexpected archive URL or length.

The updater defers checks and restart during file removal. An application termination guard also covers Sparkle's resumed-install paths. Ordinary restarts retain saved SQLite maps but clear the session-only collection. The native installer and its helpers perform replacement and relaunch; the application does not implement its own shell-based installer. [Sparkle updater delegate](https://sparkle-project.org/documentation/api-reference/Protocols/SPUUpdaterDelegate.html).

Current releases use ad-hoc code signatures because no Apple Developer ID is available. Sparkle's release signatures authenticate later updates independently; initial internet downloads still require macOS approval. The optional Developer ID path signs nested code, submits it for notarization, staples the result, and only then creates the signed update archive. That path requires credentials and has not been exercised against Apple's service. See RELEASING.md.

Orbit Disk separates filesystem work from searching. A background scan reads names and size metadata, builds a folder tree, and totals sizes from the leaves upward. The result is persisted in a local SQLite index. Opening a saved folder loads its direct children and a bounded preview of larger descendants. Name search reads indexed metadata without reopening files. File contents are never stored in the index.

This follows the useful part of instant-search tools: gather metadata once, then query an index. Everything keeps its running database in memory and indexes size information for fast searches and sorting. Its NTFS change-journal approach belongs to Windows; it is not an API available to this macOS app. [Everything indexes](https://www.voidtools.com/en-us/support/everything/indexes/) and [Everything FAQ](https://www.voidtools.com/faq/).

FSearch is another reference for keeping database construction away from queries. Its source keeps the old index when a replacement scan is cancelled. Its current monitoring documentation also describes the need to rescan at launch and the limitations of filesystem notifications. These are architecture references; Orbit Disk does not incorporate either project's source. [FSearch database implementation](https://github.com/cboxdoerfer/fsearch/blob/master/src/fsearch_database.c) and [database update documentation](https://github.com/cboxdoerfer/fsearch/wiki/Database-update).

On macOS, `getattrlistbulk` retrieves metadata for a batch of directory entries per call. Orbit Disk validates returned attributes and packed record bounds, falls back to a fresh `readdir`/`lstat` enumeration when bulk enumeration fails, and does not follow symbolic links. It skips nested mounted volumes and reports inaccessible entries. Allocated bytes for repeated hard links are counted once per device/inode pair. [Apple's getattrlistbulk manual](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/man/man2/getattrlistbulk.2).

The default map shows logical data-fork bytes, matching `st_size`. Allocated bytes describe filesystem-reported storage and are a separate figure. A sum of file sizes is not a promise of space recovered by deletion: APFS clones share storage, snapshots can retain it, directory metadata is not included, and protected files may be inaccessible. [Apple's getattrlist manual](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/man/man2/getattrlist.2) and [About Apple File System](https://developer.apple.com/documentation/foundation/about-apple-file-system).

Each scanned root has a database named by its SHA-256 path hash. Integer node and parent identifiers keep secondary indexes compact; full paths remain available through a unique lookup index. A folder view includes every direct child, then up to 2,000 preview descendants across four levels. The app can open a large saved index without decoding its entire tree. Search uses a folded filename column for case- and accent-insensitive literal matching, with a covering size index for result ordering and counts.

Filesystem events drive targeted subtree refreshes. The stored event ID and monitor identity belong to the same committed snapshot. The event checkpoint is captured before a full scan; monitoring then replays events from that checkpoint to reconcile changes made during scanning. Dropped or invalid event history requires a full refresh. The app verifies the saved monitor/volume identity before reusing its event history. Watcher setup and teardown run off the main thread because macOS may wait for folder-access consent while opening watched ancestors. Events arriving before attachment are buffered, and cancelled startup cannot attach a stale watcher. [Apple's FSEvents guide](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/UsingtheFSEventsFramework/UsingtheFSEventsFramework.html).

Every save or incremental update is prepared in a separate database and published by an atomic rename after its transaction completes. Updates first attempt an APFS file clone, then fall back to copying on other filesystems. A shared mutation lock serializes publication, and revision checks reject stale incremental updates. Cancellation, scan failure and partial incremental scans preserve the previous rows and event watermark. Incremental updates recompute affected folder totals and reassign allocated bytes across all paths sharing a file identity, including when a formerly single-link file gains another link outside the changed subtree. SQLite supplies the transaction mechanism. [SQLite atomic commits](https://www.sqlite.org/atomiccommit.html).

Permission limits remain visible. A full scan may save accessible items with warnings. An incremental scan that encounters inaccessible entries is rejected so it cannot turn missing permissions into apparent deletions. The saved map remains available; resolve folder access and perform a full refresh. Earlier partial-scan warnings remain until a complete refresh replaces them.

Verification should separate first-observed and warm filesystem runs, report file count, elapsed time and peak memory, and avoid promising an instant first scan. Use a generated wide tree of many small files and a nested tree, compare logical sizes with an independent `lstat` walk, and include sparse files, hard links, symlink loops, Unicode names, unavailable paths and cancellation. A forced fallback run should match bulk results. Large-index search latency is a separate measurement from disk scan throughput.

Observed on 26 October 2026 with a release build on this Apple M5 Mac, macOS 27.0.1: scanning a generated fixture with 20,006 files and 102 directories took 148 ms, and the initial index save took 272 ms. Across 20 subsequent operations, cached root loading had a median of 12.7 ms and filename search a median of 4.67 ms. Scanning and updating one 200-file branch took 29.4 ms. The cache occupied 9.81 MB, reduced from 21.09 MB by removing repeated path data from secondary indexes. The scan matched an independent Python `lstat` walk: 88,077,752 logical bytes and 65,576,960 allocated bytes with hard-link deduplication. The fixture included Unicode names, a symlink loop, a hard link, a 64 MiB sparse file and a resource fork.

A separate synthetic metadata benchmark indexed 200,000 files under 1,000 folders. Initial persistence took 2.07 seconds and produced a 108.0 MB cache. In a fresh process that opened only the saved database, median root loading was 14.3 ms, median search was 22.3 ms, and a 200-entry subtree update took 147 ms. Peak resident memory of that read process was 18.8 MB. These are metadata/index measurements, not a filesystem scan of 200,000 files. Filesystem caches were not cleared, and other development work was running; no cold whole-home scan or multi-million-file performance guarantee is implied.

Cleanup uses the macOS Trash API or `FileManager.removeItem` after the user reviews and confirms the chosen action. Permanent deletion has a separate confirmation and bypasses Trash. Indexed device/inode identities cover both files and folders so a replaced directory can be rejected before collection; directory identities are excluded from hard-link allocation accounting. Removal rechecks the scan root and item identities and the path policy. That policy rejects paths that resolve outside the scan and protects system locations, the scan root, the home directory, hidden configuration directories, Library directories, Trash and mounted volume roots. Filesystem permission failures remain visible; unsuccessful items remain collected, and affected parents refresh even after a partial failure. The app does not request administrator privileges.

Cursor ownership stays with the platform: SwiftUI's `.pointerStyle(.link)` on macOS 15+, and registered AppKit cursor rectangles on macOS 14. This avoids one-shot cursor changes being overwritten by later framework cursor updates. [SwiftUI pointer styles](https://developer.apple.com/documentation/swiftui/pointerstyle/link) and [AppKit cursor rectangles](https://developer.apple.com/documentation/appkit/nsview/resetcursorrects()).

Map dragging uses AppKit mouse tracking, retaining the pressed sector and original mouse-down event. The collection payload is an opaque one-use token in a declared app-owned data type; it contains no file URLs. The tray resolves that token through the current map and rechecks file identities and cleanup policy. Grouped sectors retain their actual members, batch deduplication uses ancestor path sets, and groups over 64 items validate off the main thread. Collection remains staging only. [AppKit drag sessions](https://developer.apple.com/documentation/appkit/nsview/begindraggingsession(with:event:source:)) and [Apple data-type declarations](https://developer.apple.com/documentation/uniformtypeidentifiers/defining-file-and-data-types-for-your-app).

## Responsiveness update (0.7.0)

Profiling identified repeated localized sorting of equal-sized scan entries, implicit filesystem type checks while constructing indexed URLs, and chart/group calculations repeated on hover. The scanner now breaks size ties with deterministic string ordering; the explicit Name sort retains localized ordering. Indexed URLs use the directory flag already stored in the database. The model publishes a saved map before starting event-history validation, while still checking that the scan root has the expected device/inode identity.

The chart retains its layout, group-member lookup, and collection marks across pointer and selection updates. Its cache key combines the displayed root path with a publication revision. Every new folder publication changes that revision, so same-path replacements and unchanged totals cannot hide updated metadata. Collection changes update marks without rebuilding geometry. Native stationary hover refreshes on layout or geometry changes rather than comparing every member of a large group on each view update.

The model also caches sorted rows, visible row identifiers, and the combined hover description/row relationship. Navigation, new search results, and new folder data invalidate the appropriate caches. Repeated relationship and description getters for a synthetic 100,000-item group previously took about 365 ms combined; cached getters measured below 0.001 ms. The initial relationship calculation still has a cost, so this measures eliminating repeated calculations rather than instantaneous first entry into an unusually large group.

Release measurements on the same Mac, comparing the prior implementation with this update:

| Operation | Before | After | Method |
|---|---:|---:|---|
| Scan 20,006 generated files / 102 directories | 129.0 ms | 104.3 ms | 64 warm samples per variant, interleaved |
| Scan 6,080 files / 1,612 directories | 71.4 ms | 66.6 ms | Same interleaved method, directory-heavy fixture |
| Load saved 20,006-file root | 12.5 ms | 6.2 ms | Seven interleaved process runs, median of 20 measured loads each |
| Search saved fixture | 4.06 ms | 4.07 ms | Same processes; 100 matching results, effectively unchanged |
| Save 20,006-file index | 272.8 ms | 207.6 ms | Five interleaved process runs, five saves each |
| Prepare an empty-collection chart with 20,000 direct children | 70.0 ms | 9.1 ms | Synthetic metadata; nine-run medians |
| Prepare an empty-collection chart with 100,000 direct children | 411.3 ms | 53.5 ms | Same synthetic method |

Subsequent chart preparation reuses the cached result; preparation and group-selection lookup each measured below 0.001 ms. These are calculation timings, not complete frame-rendering or input-to-display latency. A worst-case collection-mark change with one collected item at the end of a 100,000-member group still took about 275 ms, once per collection change instead of on every hover. The wide filesystem fixture's logical and allocated totals were unchanged; bulk and fallback scans also matched the independent directory-heavy fixture totals.

A final combined model benchmark included the new scanner, index and model changes together. Two process runs per variant in reversed order each measured six fresh scan/save cycles and six cached reopens on the 20,006-file fixture. The median of those run medians improved from 506.3 to 386.5 ms for publishing the first map, and from 21.6 to 13.4 ms for reopening it. In-memory back navigation improved from 2.86 to 1.86 ms; indexed subfolder navigation was effectively unchanged at about 4 ms. Publication timings exclude SwiftUI rendering and still use warm filesystem caches.

These runs used warm filesystem caches and generated data. They do not imply an instant first scan of Home or an entire Mac. First use still reads all accessible metadata and persists an index; normal reopening, navigation, search, and pointer feedback reuse saved or prepared data. Invalid journal history or a replaced root still triggers reconciliation or a new baseline as appropriate.

## Progressive mapping (0.8.0)

The first scan now exposes a browsable in-memory preview. Root metadata appears before directory enumeration; each successful listing exposes discovered files and pending folders before descending into their subtrees. `pending` means traversal or allocation accounting is outstanding, `scanning` means folder totals are still growing, and `complete` means the scan attempt finished. Inaccessible entries retain their separate accessibility flag. Logical bytes, deduplicated allocated bytes, and file counts propagate through ancestors as work completes. Pending folders remain openable, and incomplete sizes are labeled as measured so far.

`DiskScanPreview` stores shallow metadata and child identifiers behind a lock. A view contains every direct child of the displayed folder, plus at most 2,000 deeper nodes across four levels; other ancestors carry totals without unrelated child rows. Size ordering is cached per folder, with name ties. New listings and changes to child logical sizes invalidate the affected ordering caches. The app checks revisions and hydrates views off the main thread, including acquiring the preview lock. Repeated polling skips unchanged revisions, and publications wait while a mouse gesture is active.

Previews never write an index or advance an event watermark. Only the finished scan result enters the existing atomic save path. Cancelling keeps the partial map browsable in memory; restarting performs a fresh scan. Finished items can be collected during mapping, while both removal routes remain blocked until the map is saved. Search uses the completed index. Navigation, selection, and collected items survive the final handoff, and a full refresh keeps an existing saved map available.

An optimized core benchmark on the generated 20,006-file fixture exposed the first usable root listing in **0.50–1.55 ms** across three preview scans. Those scans completed in **128–150 ms**; two interleaved warm scans without preview took **99.6 and 107.7 ms**, excluding the first observed run. The preview trades additional bookkeeping for earlier usable results. All runs retained the expected 88,077,752 logical and 65,576,960 allocated bytes.

A separate synthetic metadata fixture placed 100,000 files in one branch. Its first bounded root view took **32.8 ms**; the median of 19 subsequent views was **0.344 ms** after caching ordering, compared with **34.6 ms** before that cache. Opening the branch itself includes all 100,000 direct rows: **27.5 ms** initially and **24.1 ms** for subsequent views. Direct rows are intentionally outside the descendant limit. These measurements describe core data availability and hydration with warm generated data, excluding index persistence, UI polling, rendering, and input-to-display timing. They are not whole-Mac scan measurements. The 24 core checks cover early pending-folder navigation, cancellation, ordering invalidation, bounded previews, inaccessible folders, and final bulk/POSIX size parity.

Outside-click dismissal keeps native sheets and alerts. A presenter-local mouse monitor checks the attached sheet's screen rectangle and window ancestry, then changes the existing presentation binding. It ignores clicks inside the sheet or unrelated windows, and returns nil for the dismissing event to prevent activation of underlying controls. Nested presenters handle only their own topmost sheet. [Apple's local event monitor documentation](https://developer.apple.com/documentation/appkit/nsevent/addlocalmonitorforevents(matching:handler:)) describes this pre-dispatch interception and consumption behavior.

Layout stability is verified separately from scan throughput. Header and action slots, the breadcrumb row, metrics, inspector, progress footer and collection tray retain their dimensions through content changes. The chart center reserves its title, size, detail and Up slots. Contents rows have a fixed height and size/action columns; collection status shares a line with search context. The local NSTableView appearance adapter keeps its enclosing scroll view's vertical gutter reserved, removing a measured 17-point column jump between overflowing and short lists while retaining the current scroller style. Collection error text occupies a reserved header region, and Quick Look has a fixed content size. Native SwiftUI frame probes measured zero movement in tracked regions/columns across 39 states and 16 additional transition traces; details and limits are in VERIFICATION.md.

## Toolbar and list scrolling (0.9.3)

The location and actions use separate native toolbar items in a unified title bar. Their reserved widths keep content changes from moving the controls, while AppKit supplies the space between them. The header has no logo or wordmark. Only the split background extends through the top safe area; the toolbar background is hidden, and its 40-point content frames fit inside the 52-point native title bar. Body content keeps its normal safe area. Selection uses a warm fill and thick coral outline; temporary hover uses a neutral fill and thin slate outline. The collection footer retains its full drop area with no idle border or inner background.

Each Contents list shares one hover tracker attached to its native scroll view. Wheel input, clip-origin changes and live scrolling clear hover once, then suppress row callbacks through the gesture and momentum. A common-run-loop timer waits 180 ms after the last movement before resolving the visible row under the actual pointer. Restoration requires a visible key window without an attached sheet. Selection is independent and stays visible. Row references and model callbacks are weak; view teardown removes observers, the local wheel monitor and the timer. Scroll events do not publish a per-frame model state.

The native hover checks exercise wheel, gesture, momentum, scrollbar, pointer restoration, scope and teardown behavior. The layout harness uses a titled AppKit window with a real SwiftUI toolbar, checking traffic-light alignment and visible controls as well as content frames. These checks do not measure physical-device frame rate.
