# Discovery scaling: Rust port vs Swift v0.9.15

Measured 2026-11-09 on an Apple M5 (10 cores: 4 performance + 6 efficiency, 16 GB), macOS 27.0.1 (26A434), uptime 12 days. Discovery only: parallel listing into the live inventory with no index writer. Fixtures are real APFS files on the Data volume, generated by `discovery_probe fixtures`:

- `flat`: 60,008 records, one folder of 60,000 files
- `mixed`: 90,068 records in 3,662 folders, 86,406 files, with hard links, sparse files, symlinks, and long and Unicode names. This has the same shape and counts as `mixed-deep` in `docs/benchmarks/parallel-discovery.json`.

**The machine was busy.** Unrelated `node` and `clang` processes used about 3–7 cores (load averages 4–23). Every comparison below is paired: the same fixture directories, fresh processes, order alternating every round, and an unmeasured warm-up of both sides. Load averages are recorded per run. Absolute times moved by up to 2× over the session on both sides (flat: 54–130 ms). Read ratios within one table, not absolute numbers across tables.

## Result

Neither implementation gets faster with more workers on this machine today. The cause is in the kernel: the two operations discovery spends its time on, opening a directory and reading per-file attributes, are serialized system-wide. Rust is already at that floor with one worker. Paired, Rust is 1.33–1.40× faster than Swift on mixed and 1.18× on flat. No code change made a measurable paired difference, so none was kept.

## Root cause: the kernel serializes opens and attribute reads

`discovery_probe scaling` (new) times each kernel operation discovery performs, through the platform layer, on pre-opened `mixed` folders with 1–8 threads. Each value is the best of three passes over 3,600 leaf folders.

| Operation (3,600 leaves) | 1 thread | 2 | 4 | 8 |
|---|---:|---:|---:|---:|
| `open_child` (openat + fstat + close) | 63.3 ms | 67.7 | 68.8 | 66.4 |
| `child_identity` (fstatat) | 4.5 ms | 3.1 | 1.7 | 1.6 |
| `list` (getattrlistbulk, 86,400 entries) | 131.0 ms | 118.7 | 130.0 | 127.4 |
| `open_child` + `list` | 200.9 ms | 206.4 | 206.3 | 207.1 |
| `open_root` by path | 70.6 ms | 67.4 | 70.4 | 66.6 |

With `--spread same-parent`, where concurrent threads work in the same parent folder, the numbers are identical (66.5 / 130.5 / 199.8 ms). Spreading workers across parents therefore cannot help.

A C micro-benchmark (not committed) isolated the costs:

- **Opens.** Every `open`/`openat` costs about 17.7 µs and does not scale with threads. This holds for directories and regular files, with or without `O_DIRECTORY`/`O_NOFOLLOW`, and with `O_EVTONLY` or `O_SEARCH`. It also holds on a separate APFS disk image, so the serialization is global, not per volume. `close` (0.3 µs) and `fstatat` of the same names (0.6–1.2 µs, scales ~2.8×) are cheap.
- **Per-file attributes.** `getattrlistbulk` costs about 1.4 µs per file and does not scale as soon as any `ATTR_FILE_*` attribute is requested: `LINKCOUNT`, `ALLOCSIZE`, `DATALENGTH`, `DATAALLOCSIZE`, `TOTALSIZE` alone or combined, with or without `FSOPT_NOINMEMUPDATE`. With only name, type and file ID the same listing takes 1.6 ms instead of 120 ms. Disk usage needs the file attributes, so this cost cannot be avoided.
- **System-wide.** Two processes running the same loop each take twice as long (opens 63 → 123 ms, bulk 128 → 253 ms). Opens and bulk reads also slow each other down when run in parallel. No vnodes are allocated during either loop (`vfs.vnstats.num_newvnode_calls` unchanged), so vnode-table recycling is not the cause. The vnode table is full: 248,452 vnodes and 218 M recycles since boot.
- **Not a CPU shortage.** A CPU-bound loop scales perfectly to 8 threads at the same time.

Mixed discovery therefore has a floor of about 3,662 opens × 17.7 µs ≈ 65 ms plus 86,406 files × ~1.4 µs ≈ 120 ms ≈ 185–200 ms. The floor rises when other processes do filesystem work. Rust with one worker measures 190–200 ms, and `open_child + list` alone takes 201 ms, so Rust's own overhead is in the noise. Additional workers spin on the contended kernel lock: system CPU rises from 125 to 264 ms with no change in wall time.

Why Rust beats Swift on mixed and pipeline: per directory, Swift's `SecureDirectoryCursor` opens the child and then opens `"."` again for a private enumeration offset (two serialized opens). It also `lstat`s the root path twice, before the open and after the listing. Rust opens once and rewinds with `lseek`, and checks the root every 64 listings. Pipeline folders hold only 10 files, so opens dominate there and the ratio is highest (1.56–1.62×).

### Control: where the kernel parallelizes, Rust scales

The same fixtures on a fresh 400 MB APFS disk image (`hdiutil`, latency-bound I/O) let `getattrlistbulk` scale (2.3× at 4 threads in the micro-benchmark), while opens stay serialized. There, both implementations scale (paired, 7 rounds, load 6.6–6.8):

| mixed on disk image | 1 worker* | 2 | 4 | 8 |
|---|---:|---:|---:|---:|
| Rust | 880 ms | 499 ms | 383 ms | 396 ms |
| Swift | 983 ms | 552 ms | 479 ms | 453 ms |

\* 1-worker column from a separate 3-round run.

Rust scales 2.3× by 4 workers and stays ahead of Swift at every count. The work-stealing scheduler, the live-inventory lock and the spool are therefore not what limits scaling on the Data volume.

## User-space contention (profile)

`sample` of `discovery_probe profile --fixture mixed --workers 4` over 5 s: worker stacks were 61–65% in `getattrlistbulk`, 26% in `openat`, and about 1% each in `fstatat`, `fstat` and `close`. `publish` (`LiveInventory::append` under the live write lock) took about 7%. Of that, parking_lot spin-yields on the live `RwLock` (`swtch_pri`) were about 3% of worker samples. Spool, mailbox and scheduler took under 0.1%, and there was no `__psynch_cvwait`/`__ulock_wait` on workers. Cursor revalidation is one `fstatat` per cached ancestor (3,556 per run, ≈ 4 ms of CPU, and it scales). The periodic root check costs 57 opens per run, ≈ 1 ms. User-space work is 10–20 ms in total and overlaps the kernel work once there are two or more workers.

## What was tried

| Change | Result (paired) | Decision |
|---|---|---|
| Workers at `USER_INITIATED` QoS (new `Platform` thread hook, as Swift's discovery queue). | Natural load: mixed (4 workers) 197.4 → 193.3 ms, flat 108.7 → 108.1 ms (n = 9). With 10–12 extra default-QoS CPU burner threads: mixed 209.3 → 205.5 ms, flat 116.4 → 116.3 ms (n = 9); an earlier n = 5 run was mixed 1 worker 200.7 → 202.8 ms. The ±2% differences are inside the run-to-run spread. | Reverted: not a measured win. |
| Spread workers over different parent folders. | `scaling --spread same-parent` vs split parents is identical for opens and listings. | Not implemented: no effect possible. |
| Batch live-inventory appends per worker. | The lock is ≈ 3% of worker time and overlaps kernel time at 2+ workers. It is only on the critical path with 1 worker, where all user time is 10 ms of 192 ms. | Not implemented: below the noise floor. |
| Drop redundant `fstatat`/open (revalidation, root check). | ≈ 4 ms CPU (parallel) and ≈ 1 ms serialized per run, under 0.5% of wall time. | Not implemented: not measurable. |
| `getattrlistbulk` without a separate identity open; larger buffers. | Every listing needs one open, and Rust already does exactly one per directory. Per-call overhead is negligible: 7,200 calls with name-only attributes take 1.6 ms in total. | Not implemented. |
| `O_SEARCH`, `O_EVTONLY`, plain `O_RDONLY` opens; `FSOPT_NOINMEMUPDATE`; minimal file-attribute sets. | All cost the same (micro-benchmark); `getattrlistbulk` fails on an `O_SEARCH` descriptor. | No change possible. |

The default stays at 4 workers. On today's warm Data volume, 1–8 workers give the same wall time; on latency-bound storage, 4 workers are 2.3× faster than 1.

## Reproduce

```sh
# The Swift probe and its build script were removed after the port; both remain at tag v0.9.15
# (scripts/benchmarks/build-discovery.sh). The Rust side:
cargo xtask bench-compare --suites discovery,pipeline --rounds 5 --output <new dir>
# Kernel operations alone, and a long-running process for `sample <pid>`:
cargo run --release -p orbit-bench --bin discovery_probe -- fixtures --dir <dir outside /private/tmp>
cargo run --release -p orbit-bench --bin discovery_probe -- scaling --dir <dir> [--spread same-parent]
cargo run --release -p orbit-bench --bin discovery_probe -- profile --dir <dir> --fixture mixed --workers 4
```

`DiscoveryProbe producer ROOT WORKERS RECORDS FILES` runs `AsyncListingProducer` with a `LiveMappingInventory` and no seed, reuse or writer, which matches `discovery_probe sample`. `DiscoveryProbe stage ROOT NEW-CACHE RECORDS FILES` runs the documented stage configuration. The build script raises v0.9.15's four-worker clamp in the benchmark copy only and records the patch in `manifest.json`. Keep fixtures out of `/tmp`: Foundation strips `/private` from the Swift probe's paths.
