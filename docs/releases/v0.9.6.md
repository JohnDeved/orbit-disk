Orbit Disk 0.9.6 keeps mapping in the background while you browse, collect, and remove files. This release includes the performance and recovery work since 0.9.5.

## Mapping that keeps its progress

- Mapping saves directory listings and traversal progress as it goes. Switching locations leaves the scan running; returning restores the last prepared folder and selection. Stopping, restarting, or reopening the app resumes committed progress.
- Opening a child folder can reuse its parent's active, stopped, or saved map. A parent scan can also reuse compatible completed child maps. The scanner prioritizes the folder you open and chooses native enumeration for tiny listings where copying cached rows would cost more.
- The finished map is published from its staged database, replacing the old full-tree save at the end. The previous saved map remains available while a replacement is built.
- Mapping uses fewer durable commits, reuses database statements and identity indexes, and indexes its pending-directory queues. It preserves the existing durability guarantees and batch limits.
- Recovery checks removal history in batches and yields between them, reducing the wait to reopen a map and contention with new deletions. Failed mapping sessions reopen their durable work instead of remaining stuck.

Committed work survives interruption; an unfinished listing can need another read. Replaced folders, incompatible filesystem history, and explicit full refreshes can still require rescanning.

## Keep using the files already visible

- Drag visible files and folders from the graph or list into the collection while mapping continues. Review, move to Trash, and permanently delete validated entries without waiting for the complete map.
- Collection requests queue within their original mapping session. Accepted drops survive another drag or a location switch while macOS delivers the drop data.
- Large drops validate in small rotating batches, so a newer small request can proceed. Validated items appear progressively; expensive validation, collection preparation, row removal, and deletion completion run away from the UI thread.
- Collection snapshots cache their membership and total size, avoid repeated ancestor walks, and combine later publications into larger batches. Delete confirmations retain the reviewed set while subsequent additions wait; Clear Collection cancels pending additions.
- Successful removals disappear immediately while index reconciliation continues. Search counts, folder totals, and subsequent mapping account for those removals, including after interruption.

## Faster navigation, graphs, and search

- Large folder views prepare row identities, lookups, and colors in the background. Navigation cancels obsolete reads and preparations. Large name sorts leave the current list usable while sorting.
- Large reorderings rebuild the native list in one step and restore the visible row, scroll offset, selection, and focus. Sorting and refresh publication wait for an active drag to finish.
- Dense graphs reuse prepared paths, child arrays, membership sets, and colors. Whole-ring groups avoid redundant copies; same-folder refreshes reuse compatible hover membership. Collection marks check the smaller collected set instead of walking every group member.
- Graph hit testing searches a grid of nearby candidates. Linking graph hover to a large list uses a cached row lookup for its current order.
- Partial maps are searchable during mapping. Search skips unnecessary file-object construction, avoids a second database pass for empty results, and cancels obsolete work. Search history no longer retains every previously seen result.
- Saved folder loading reuses descendant queries. Incremental refresh batches hard-link accounting, recalculates only affected ancestors, reuses refresh-planning metadata, and replaces pairwise path comparisons with a set and ancestor walk. Changed hard-link paths stream from SQLite instead of accumulating in an array.
- Index saves do less ordinary-path parsing. Volume discovery and filesystem-event normalization run away from the UI thread, coalescing or bounding queued work so they do not block interaction.

## Measured improvements

These are targeted before-and-after tests of the optimizations developed for this release, not one end-to-end comparison of 0.9.5 with 0.9.6. They use local generated data and warm caches. Most measure core or model work; offscreen UI measurements are identified below.

| Workload | Before | After |
|---|---:|---:|
| Durable traversal of 100,000 files, filesystem enumeration versus compatible map reuse; excludes final publication and UI | 4.19 s | 1.77 s |
| Resume first view with 5,000 unrelated removal-history entries and a concurrent journal writer; core only | 5.29 s | 1.48 s |
| Map 2,000 empty folders after removing one durable commit per directory; app model | 709 ms | 637 ms |
| Replace a 20,000-file indexed folder, including publication but excluding enumeration | 640 ms | 322 ms |
| Plan refreshes for 500 changed folders | 219 ms | 73 ms |
| Load a saved folder containing 20,000 empty directories; data loading only | 372 ms | 251 ms |
| Install a prepared 100,000-file folder and access its first row on the UI thread | 195 ms | 25.7 ms |
| Refresh a 100,000-file whole-ring graph after model installation; offscreen hosted view | 97.4 ms | 68.3 ms |
| Update collection marks in a 100,000-member graph through offscreen raster capture | 64 to 81 ms | 0.88 to 2.32 ms |
| Search with no matches in a one-million-entry saved index; excludes debounce | 78.3 ms | 38.2 ms |
| Search a partial map with 20,000 varied-size matches; core only | 26.9 to 28.3 ms | 10.6 to 11.7 ms |
| Process footprint after 100 different searches in a 260,000-entry model fixture | 41.7 MiB | 7.7 MiB |
| Peak memory during an incremental update of a synthetic 100,000-pair hard-link index | About 101 MB | About 77 MB |

Durable progress and progressive collection updates add bookkeeping. They can take more total time than the former in-memory, all-at-once paths; this release prioritizes retaining work and making results usable sooner. These measurements do not promise an instant first scan of a Mac or a particular frame rate. Full methods, sample sizes, additional measurements, and tradeoffs are in [the technical notes](https://github.com/JohnDeved/orbit-disk/blob/v0.9.6/TECHNICAL-NOTES.md).

## Build fixes

- Screenshot generation uses the current collection model.
- The cached-view regression check synchronizes with background refresh, eliminating a timing race without weakening its assertions. Optimized app checks now print failure details in CI.
- The reentrant search check always starts a distinct query, regardless of filesystem listing order.
- Build and Release run independent regression suites in parallel. Publishing still requires every check to pass.
- Versioned release notes are included automatically when publishing.
